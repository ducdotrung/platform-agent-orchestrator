# ADR-0003: Persistence, Checkpoints, Idempotency, Audit, and Retention

- Status: accepted for the public hackathon sample
- Date: 2026-07-30
- Decision owners: Repository Owner and Repository Maintainer (sample roles)
- Scope: PostgreSQL topology, application records, checkpoint isolation,
  idempotency, side-effect receipts, audit, migrations, and retention
- Depends on: ADR-0001 and ADR-0002

## Context

The control plane needs several durable stores with different authority and
retention semantics:

- accepted event and workflow-run business state;
- delivery jobs, attempts, leases, retries, and dead letters;
- LangGraph checkpoints and pending writes;
- API idempotency decisions;
- external side-effect claims and receipts;
- human approvals and operator actions;
- a durable audit trail.

Combining these concepts in graph state would expose credentials or payloads,
make business queries depend on LangGraph internals, and confuse telemetry with
audit. Combining their transactions is also impossible where a checkpoint or
external side effect commits independently of application state.

The public sample contains synthetic alerts and public Sock Shop references,
but it should demonstrate boundaries that can later be re-evaluated against
company classification, backup, encryption, and deletion policy.

## Decision

Use one PostgreSQL server for the public sample with two separate databases:

```text
PostgreSQL server
├── platform_agent
│   └── orchestrator schema (application-owned, Alembic-managed)
└── platform_agent_checkpoints
    └── saver-owned objects (LangGraph setup/migrations only)

External systems
├── Langfuse / Prometheus telemetry (non-authoritative)
└── local demo notifier (side-effect receipt recorded in platform_agent)
```

There are no cross-database or distributed transactions. Recovery relies on
stable IDs, idempotent operations, checkpoints, and reconciliation.

The application database uses SQLAlchemy 2.x async models and one
`AsyncSession` per transaction/task. Sessions are passed explicitly and never
shared across concurrent tasks. Alembic owns application migrations. The
checkpoint database uses the supported `AsyncPostgresSaver`; application code
must not query or migrate saver tables directly.

## Store authority

| Question | Authoritative store |
| --- | --- |
| Was an event accepted and deduplicated? | `events` plus `idempotency_claims` |
| Was a signed webhook nonce already used? | `auth_replay_claims` |
| What user-visible state is the run in? | `runs` |
| Is work pending, leased, retrying, or dead-lettered? | `delivery_jobs` and `delivery_attempts` |
| Where can graph execution resume? | LangGraph checkpoint database |
| Was an approval accepted, rejected, or stale? | `approvals` plus audit |
| Was a logical notification attempted or delivered? | `side_effects` |
| Who or what caused a controlled transition? | `audit_events` |
| What happened in traces or metrics? | Telemetry backend; never authoritative for the questions above |

## Application schema

All application tables live in the explicit `orchestrator` schema. UUID primary
keys are generated by the application without requiring a PostgreSQL extension.
Timestamps use database-generated `timestamptz`. Status columns use text with
check constraints so migrations are not coupled to PostgreSQL enum alteration.

Every mutable table includes an integer `version` used for optimistic
concurrency where a lease token is not the stronger fence. All scope-sensitive
unique constraints include `scope_id`, even though the public sample has one
fixed scope. This prepares keys for authorization without claiming tenant
isolation; ADR-0004 decides access policy.

### `events`

Authoritative accepted-event and admission-deduplication record.

Required fields:

- `id`, `scope_id`, `source`, `event_type`, `schema_version`, `subject`;
- `occurred_at`, `received_at`, `correlation_id`;
- `idempotency_key`, 32-byte SHA-256 `fingerprint`;
- bounded canonical `payload` JSON and `payload_purged_at`;
- `version`.

Constraints:

- unique `(scope_id, source, idempotency_key)`;
- fingerprint length is exactly 32 bytes;
- canonical payload is at most 64 KiB serialized;
- one event maps to at most one initial run in the public sample.

The fingerprint remains after payload purge so later reuse of the key can still
return the original result or detect a conflict during the retention window.

### `runs`

Authoritative user-facing execution summary, not a checkpoint copy.

Required fields:

- `id`, `scope_id`, `event_id`, `workflow`, `workflow_contract_version`;
- nullable `replay_of_run_id` for an operator-created replay;
- stable `thread_id` equal to the run ID string;
- state from ADR-0002 and integer `version`;
- bounded `result_summary`, `error_category`, and error fingerprint;
- `created_at`, `started_at`, `interrupted_at`, `finished_at`;
- future immutable release identifier, nullable until D05;
- `checkpoint_deleted_at` retention marker and nullable `operator_closed_at`.

Constraints:

- partial unique `event_id` where `replay_of_run_id` is null, so admission can
  create only one initial run;
- replay runs link the original run and use the same event and scope;
- unique `(scope_id, thread_id)`;
- result summary at most 16 KiB and error summary at most 2 KiB;
- terminal timestamps agree with terminal states.

Runs store identifiers, status, and bounded summaries. They never store the full
graph state, prompt, completion, evidence body, or tool output.

### `delivery_jobs`

Authoritative queue state defined by ADR-0002.

Required fields:

- `id`, `scope_id`, `run_id`, `kind` (`invoke` or `resume`), immutable
  `operation_key`;
- job state, `available_at`, `attempt_count`, `max_attempts`;
- `lease_token`, `lease_owner`, `lease_expires_at`, `last_heartbeat_at`;
- bounded last error category/fingerprint;
- `created_at`, `completed_at`, nullable `operator_closed_at`, `version`.

Constraints and indexes:

- unique `(scope_id, run_id, kind, operation_key)`;
- pending/retry partial index on `(available_at, created_at, id)`;
- leased partial index on `(lease_expires_at, id)`;
- lease fields are all present only in `leased` state;
- `0 <= attempt_count <= max_attempts`;
- no event payload is duplicated into the job.

### `delivery_attempts`

Bounded attempt history for recovery and operator diagnosis.

Required fields:

- `id`, `job_id`, `attempt_number`, `lease_token`, `worker_id`;
- `started_at`, `last_heartbeat_at`, `finished_at`;
- outcome, error category/fingerprint, retry `available_at` if any, and
  `version`.

Constraints:

- unique `(job_id, attempt_number)` and unique `(job_id, lease_token)`;
- no raw exception, model response, tool output, or payload;
- one active attempt per job, enforced with a partial unique index.

The claim transaction creates the attempt row and updates the job/run together.
Heartbeat and completion update both the job and its current attempt using the
lease token fence. When reclaiming an expired lease, the same claim transaction
first closes its active attempt with outcome `worker_lost`, then creates the
next attempt. This preserves the one-active-attempt constraint.

### `idempotency_claims`

Durable API and operator request identity. Domain tables retain their own
unique constraints as defense in depth.

Required fields:

- `id`, `scope_id`, boundary (`admission`, `approval`, `operator_replay`);
- idempotency key and 32-byte request fingerprint;
- status (`in_progress`, `succeeded`, `failed_terminal`);
- resource kind/ID and bounded response status/summary;
- `created_at`, `completed_at`, `expires_at`, `version`.

Constraints:

- unique `(scope_id, boundary, idempotency_key)`;
- the same key with a changed fingerprint is always a conflict;
- response summary is at most 8 KiB and contains no credential or raw payload;
- claims are retained at least as long as the resources they protect.

The claim, domain mutation, and final replayable response summary commit in one
application transaction where possible. If an API transaction rolls back, its
claim rolls back too.

### `auth_replay_claims`

Short-lived durable replay fence for the signed-webhook profile in ADR-0004.
It is distinct from business idempotency: a retried business request uses a new
signature nonce and the same idempotency key.

Required fields:

- `id`, bounded `authenticator_id`, and 32-byte SHA-256 nonce hash;
- 32-byte signed-request fingerprint;
- signature `created_at`, `expires_at`, and `retention_until`.

Constraints:

- unique `(authenticator_id, nonce_hash)`;
- rows are immutable until retention deletion;
- the raw nonce, signature, authorization header, key, and request body are not
  stored;
- the claim commits in the same transaction as the authorized mutation and
  rolls back with it.

Expired claims remain until ten minutes after signature expiry, so replicas and
restarts enforce the same replay window. ADR-0004 defines signature validation,
nonce size, safe retry, and error behavior.

### `approvals`

Authoritative human decision for a durable interrupt.

Required fields:

- `id`, `scope_id`, `run_id`, positive integer `approval_version`;
- decision (`approved` or `rejected`), actor ID/type, bounded reason;
- 32-byte action/interrupt hash, `decided_at`, `expires_at`;
- request idempotency claim ID and `version`.

Constraints:

- unique `(run_id, approval_version)`;
- reason at most 2 KiB;
- expired, stale, changed-hash, or repeated decisions cannot create a resume
  job;
- approval plus resume job/run transition commits in one transaction.

Actor trust, authentication, and authorization are defined in ADR-0004.

### `side_effects`

Authoritative idempotency and reconciliation record for a logical external
effect. It is separate from the delivery lease because a job can be replayed
while the logical effect identity remains stable.

Required fields:

- `id`, `scope_id`, `run_id`, effect kind, destination/provider;
- idempotency key and 32-byte canonical request hash;
- state (`reserved`, `in_progress`, `retry_wait`, `succeeded`,
  `failed_terminal`, `unknown`);
- claim token/expiry, attempt count, bounded receipt and provider reference;
- `available_at`, `reserved_at`, `started_at`, `completed_at`, `reconciled_at`,
  `version`.

Constraints:

- unique `(scope_id, effect_kind, idempotency_key)`;
- the same key with a different request hash is a terminal conflict;
- receipt is at most 16 KiB, allow-listed, and never contains credentials or a
  full provider response;
- only `succeeded` supplies a successful delivery result;
- a confirmed retryable failure moves to `retry_wait` with persisted jittered
  `available_at`;
- `unknown` must reconcile by provider/idempotency key before retry.

Side-effect protocol:

1. in a short application transaction, create or claim the stable effect and
   audit the intent;
2. commit before calling the external adapter;
3. call outside any database transaction, passing the stable idempotency key;
4. in a second transaction, persist the bounded receipt/outcome and audit it;
5. after a crash or ambiguous timeout, reconcile before retrying;
6. do not enable a production adapter that supports neither provider-side
   idempotency nor lookup/reconciliation.

The local demo notifier returns a deterministic receipt and exercises this
protocol without an external network side effect.

### `audit_events`

Durable application audit trail. It is append-only to runtime roles, but it is
not described as cryptographically immutable or as a substitute for a company
security ledger.

Required fields:

- monotonic database identity, `scope_id`, database timestamp;
- actor type/ID, action, outcome, reason code;
- optional logical event/run/job/approval/side-effect IDs;
- request/correlation ID, prior/new state, action hash;
- allow-listed metadata at most 8 KiB.

Rules:

- business state and its audit event commit in the same application transaction;
- intent and outcome around an external call are separate audit events;
- no foreign key prevents retained audit metadata from outliving a deleted
  business row; IDs remain bounded locators, not embedded records;
- runtime roles can insert and read permitted rows but cannot update/delete;
- only the retention role can delete expired audit rows in bounded batches;
- audit events never contain credentials, event payloads, evidence bodies,
  prompts, completions, tool bodies, or full exception text.

## Transaction boundaries

| Operation | One application transaction contains | Deliberately outside |
| --- | --- | --- |
| Event admission | Optional signed-request replay claim, idempotency claim, event, run, invoke job, admission audit | Workflow/checkpoint work |
| Job claim | Fenced job lease, delivery attempt, run transition, claim audit | Graph execution |
| Heartbeat | Fenced job/attempt timestamps only | Graph/external call |
| Retry/terminal outcome | Fenced job, attempt, run state, bounded audit | Checkpointer internals |
| Human approval | Idempotency claim, approval, run state, optional resume job, audit | Graph resume execution |
| Side-effect reserve | Stable effect claim and intent audit | External call |
| Side-effect outcome | Fenced receipt/state and outcome audit | External call already completed |
| Operator replay | Idempotency claim, new linked job/run, annotation, audit | Automatic replay |

Each transaction creates its own `AsyncSession`; concurrent tasks never share a
session. Database transactions are short and contain no network, model, MCP,
telemetry, or LangGraph invocation.

Checkpoint writes commit independently through the saver. Therefore:

- a checkpoint may be ahead of the application run summary after a crash;
- a job may remain leased after a checkpoint commit;
- recovery reclaims the job, loads the same thread, and reconciles durable
  side-effect records;
- application code never attempts a two-phase commit with the checkpointer.

## Checkpoint database

Use the full-history `AsyncPostgresSaver` from a pinned compatible
`langgraph-checkpoint-postgres` release. Do not use the shallow saver for the
first slice because interruption/resume and recovery tests need checkpoint
history.

Rules:

1. `thread_id` is the stable run ID string and is never reused by another run.
2. The graph/checkpointer manages checkpoint IDs, namespaces, pending writes,
   and table layout.
3. A dedicated setup/migration command calls `await checkpointer.setup()`; API
   and worker startup only verify readiness and never run DDL.
4. Application migrations and SQL never inspect, join, update, or delete saver
   tables.
5. Retention calls `await checkpointer.adelete_thread(thread_id)` through the
   supported saver API; it does not issue table-specific deletes.
6. Set `LANGGRAPH_STRICT_MSGPACK=true` or configure an explicit minimal
   deserialization allow-list. Pickle fallback is prohibited.
7. Graph state contains only bounded validated payloads, identifiers, evidence
   references, decisions, approvals, and summaries. It excludes credentials,
   complete source corpora, raw model/tool traffic, live clients, and audit
   history.
8. The public synthetic sample does not require application-level checkpoint
   encryption. Before company reuse, approved at-rest encryption and whether to
   add LangGraph's encrypted serializer must be decided from classification and
   key-management policy.

Checkpoint deletion is idempotent across databases:

1. select a terminal run whose checkpoint retention elapsed and whose
   `checkpoint_deleted_at` is null;
2. call `adelete_thread(run_id)`;
3. after success, set `checkpoint_deleted_at` and append a retention audit event
   in the application database;
4. retrying after an unknown outcome is safe because deleting an absent thread
   is treated as success.

## Migration ownership

Application database:

- SQLAlchemy models define the expected schema;
- reviewed Alembic revisions are the deployed DDL authority;
- autogeneration may propose a revision but does not approve it;
- migration jobs use a dedicated role and run before API/worker rollout;
- runtime roles have no DDL permission;
- startup fails readiness on an incompatible application revision;
- use expand/migrate/contract changes where a rolling deployment requires
  compatibility; destructive downgrade is not the rollback strategy.

Checkpoint database:

- the pinned saver package owns its setup and migrations;
- a dedicated checkpoint migration job runs `setup()` before workers;
- runtime code never patches vendor migrations;
- package upgrades require checkpoint create/resume/delete integration tests
  against a database copied from the prior supported version.

## Retention policy for the public sample

These are demonstration defaults, not company policy. Retention is measured
from a run's terminal timestamp using database time. Active, queued, running,
retrying, dead-lettered pending review, quarantined pending review, and
waiting-approval runs are never automatically purged.

| Data | Sample retention | Action | Owner |
| --- | --- | --- | --- |
| Accepted event payload | 30 days after terminal run | Replace payload with an empty tombstone; keep identity/fingerprint | Retention Maintainer |
| Checkpoint thread | 30 days after terminal run | Delete with `adelete_thread`, then mark application run | Retention Maintainer |
| Runs, events metadata, jobs, attempts | 180 days after terminal run | Delete children then parents in bounded batches | Retention Maintainer |
| API idempotency claims | 180 days and never before protected resource expiry | Delete after resource retention | Retention Maintainer |
| Signed-request replay claims | 10 minutes after signature expiry | Delete expired immutable claims in bounded batches | Retention Maintainer |
| Approvals | 180 days after terminal run | Delete with run-related business records | Retention Maintainer |
| Side-effect claims/receipts | 180 days after terminal run | Delete only after retry/reconciliation window closes | Retention Maintainer |
| Audit events | 180 days | Delete independently in bounded batches | Retention Maintainer |
| Telemetry | Separate backend policy | Not controlled by application retention jobs | Telemetry Owner |

Additional rules:

- approval expires after seven days in the sample; maintenance transitions the
  run to terminal `failed_terminal` with category `approval_expired` before the
  terminal retention clock begins;
- event payload purge is idempotent and records `payload_purged_at` plus an
  audit event without copying the payload;
- business deletion waits until checkpoint deletion is confirmed;
- dead-letter/quarantine records require an audited operator close decision and
  persisted `operator_closed_at` before their retention clock begins;
- retention selects and deletes bounded batches with resumable cursors; it
  never performs an unbounded table delete in the service process;
- retention failures are metrics/alerts backed by database state, not audit
  conclusions inferred from telemetry;
- the local sample creates no automated backups. Any future backup/PITR policy
  must align backup expiry with deletion commitments before company use.

## Database roles and connection ownership

ADR-0004 defines identity and grants. This ADR requires distinct logical roles:

| Role | Store access boundary |
| --- | --- |
| Application migrator | DDL on `platform_agent.orchestrator`; no checkpoint access |
| API runtime | Bounded application reads/writes; no DDL/checkpoint access |
| Worker runtime | Jobs, runs, attempts, side effects, audit; no DDL |
| Checkpoint migrator | Saver setup on checkpoint database only |
| Checkpoint runtime | Saver-managed DML on checkpoint database only |
| Retention maintainer | Approved deletion/tombstone routines; no application serving |

Credentials remain in process configuration/secrets, never events, graph
state, audit metadata, logs, traces, or database rows other than PostgreSQL's
own role catalog.

## Alternatives considered

### One PostgreSQL server, separate application and checkpoint databases

Accepted for the sample. It keeps one infrastructure dependency while making
ownership, migrations, credentials, backup/restore, and deletion boundaries
visible.

### One database and shared application schema

Rejected. Application migrations or queries could accidentally depend on saver
table names, and retention permissions would be harder to constrain.

### One atomic transaction for jobs, checkpoints, audit, and side effects

Rejected. The saver and external systems commit independently; pretending to
have atomicity would obscure the recovery gaps that idempotency must handle.

### Telemetry as audit or run history

Rejected. Telemetry can be sampled, delayed, redacted, unavailable, or deleted
under a different policy.

### Store full evidence, source, prompts, and tool results for debugging

Rejected. Checkpoints and application state contain bounded references and
summaries. Protected evaluation data belongs in its approved dataset location.

## Consequences

### Benefits

- Every operational question has one named authoritative store.
- Application and saver migrations cannot silently modify each other.
- Idempotency survives job and graph replay.
- External side-effect ambiguity has a durable reconciliation record.
- Audit and retention do not depend on optional telemetry.
- Public sample data limits are explicit and testable.

### Costs and risks

- Two databases require two pools, migration checks, health checks, and restore
  exercises even on one server.
- Application/checkpoint summaries are eventually reconciled, not atomic.
- Retention requires cross-database idempotent coordination.
- SQLAlchemy, Alembic, Psycopg, and the saver package add compatibility work.
- A public sample retention policy must be replaced, not copied blindly, for
  company data.

## Verification required by later tasks

- Application migrations upgrade an empty database and the previous supported
  revision.
- Saver setup, invoke, interrupt, restart, resume, and `adelete_thread` pass on
  the pinned package.
- Runtime roles cannot run DDL or access the other database.
- Database constraints reject conflicting event, approval, job, and side-effect
  idempotency keys.
- Repeated signed-request nonces are rejected across replicas and restart while
  a newly signed retry with the same business idempotency key remains safe.
- Side-effect crash points reconcile without duplicate logical notification.
- No graph checkpoint or audit row contains forbidden content.
- Strict msgpack deserialization rejects unapproved custom types.
- Retention skips nonterminal runs, tombstones payloads, deletes checkpoints via
  the API, and preserves idempotency through the promised window.
- Audit remains queryable when telemetry is disabled or failing.
- Restore exercises recover both databases and reconcile their run/thread IDs.
